# 設計と計測の記録

確度の表記: 【実測】手元で計測・再実行で確認 / 【公式】一次文書・ソース / 【既報】第三者の報告 / 【推測】未検証

## 背景

GitHub Copilot で C++ の呼び出し箇所を探すと、LSP(clangd)を渡しても、ripgrep より遅くトークンも多く使う。このリポジトリは、clang で事前に作った索引を、エージェントが少ない往復で確実に引けるようにする道具を作り、効果を測りながら進めるためのものである。

- 勝ち筋は rg より速いことではなく、**同名が多い検索で、確実な答えを少ない往復で返すこと**に置く
- 問い合わせのたびに解析すると rg には勝てない。Windows + D3D12 + STL の最小 TU(前処理後 22 万行)の解析に 0.53 秒、rg は Nox 全体で 50〜90 ms【実測】

- 対象は C++(と、同じ clang で解析できる C・Objective-C++)に限る。ほかの言語(C# など)はこのリポジトリでは扱わない

## 段階

| 段階 | 内容 | 次へ進む条件 | 状態 |
|---|---|---|---|
| 1 | libtooling の結果を TSV に出し、エージェントは rg で引く | 同等の正答率でトークンか往復が減る | 境目(下記) |
| 2 | 問い合わせ CLI(`ltq`) | 段階 1 の TSV では足りないと実測できた | 正答 12/12、入力 −56% |
| 3 | MCP の薄い包み | CLI と比べて選択率かトークンが改善する、または権限の面で有利 | 指示ありで正答 12/12、入力 −47%(Nox)。別のコードベース(コードベース B)では 11/12、−57%。既定の使い方にする |

トークン削減の基準は 20% とした。

## LSP が負ける原因

| 原因 | 証拠 |
|---|---|
| 渡しても使われない | Copilot CLI で LSP を渡した 8 回とも、`lsp` の呼び出しは 0 回【実測】。自発的に LSP を選んだ率は位置特定で 0〜6%、参照検索で 45〜57%【既報】 |
| 指示で使わせても安くならない | 「LSP を使え」と指示すると 1 回 2〜3 回使われたが、確認の `view` と rg も減らず、入力は rg のみの 2.3 倍【実測】 |
| 参照先のソース行が返らない | 位置だけなので、結局 `view` で読みに行く【実測】 |
| 起動直後は黙って不完全な結果を返す | 同じ問い合わせが 1 件 → 約 10 秒後に 3 件【実測】 |
| テンプレートの実体化を索引しない | clangd は `IndexImplicitInstantiation` を設定していない【公式】 |

## clang で解決できること・できないこと

| 課題 | 解決 | 方法・注意 |
|---|---|---|
| テンプレートの実体化の中の呼び出し | ○ | `clang::index` の `IndexImplicitInstantiation`。`DeferIndexingToEndOfTranslationUnit` は指定しない(実体化が届く `HandleTopLevelDecl` が無視される)【公式: IndexingAction.cpp】 |
| 実体化されないテンプレートの非依存名 | ○ | clang-cl の既定(遅延テンプレート解析)では消える。ltidx は `/Zc:twoPhase` を足す【実測】 |
| 実体化されないテンプレートの依存名 | △ | 解決先は原理的に無い。`?::f` の `dep` 行として名前だけ出す |
| テンプレート内の `using Base::f;` 越しの呼び出し | ○ | 索引は `UnresolvedUsingValueDecl`(`派生::f`)にしか向けない。TU の終わりに実体化の `UsingShadowDecl` を引いて、宣言の先も出す(`call-using`)【実測】 |
| コメント・無効な `#if` の中の一致 | ○ | 範囲を記録し、rg の一致が索引に無い理由として返す【実測】 |
| Debug/Release などの構成の差 | ○ | 構成ごとに索引を作り、ltq が和集合にして引く。USR は構成で変わる(`size_t`、`TCHAR` など)ので、修飾名・役割・位置で突き合わせる。一部の構成にしか無い行には構成名を付ける【実測: コードベース B の Debug と Release】 |
| 仮想関数の呼び出し(基底のポインタ越し) | △ | clang は基底のメソッドに解決する。実際に走るメソッドは実行時の型で決まる。ltidx は上書きの関係(`RelationOverrideOf`)を `override` 行に出し、ltq は「問い合わせが上書きしている基底のメソッドへの呼び出し」と「問い合わせを上書きしているメソッド」を別の節に出す【実測】 |
| 関数ポインタ・`std::function`・コールバック | × | 関数を取得した場所(`ref`)は出るが、どこから呼ばれるかは静的には分からない |
| `#if 0` の中の `#include` | × | どの TU にも現れないファイルとして検出する |
| リフレクション・文字列経由の呼び出し | × | 原理的に不可。「0 件 ≠ 未使用」 |

## 構成の統合と鮮度

- **構成の統合**: `.index` の中の索引本体(`<構成名>.tsv`)をすべて読み、(修飾名, 役割, 呼び出し元, 位置)が同じ行を 1 つにまとめる。そのファイルを読んだ構成の一部にしか無い行には `[only in <構成名>]` を付ける
  - 無効な `#if` は、そのファイルを読んだすべての構成で無効なときだけ「無効」とする。1 つでも有効な構成があれば、そこで索引に無い一致は「その他」になる
  - コードベース B の Debug と Release を統合すると、`#ifndef NDEBUG` の中のメンバー変数の参照 4 件と定義に `[only in index]`(Debug)が付いた【実測】
- **行の付け直し**: 索引の各行にはソース行の文字列(前後の空白を除き 200 バイトまで)があるので、索引の後に変わったファイルでは、その文字列を今のファイルから探して行番号を付け直す
  - 手がかりには、問い合わせに合う行だけでなく、そのファイルの索引の全行を使う
  - まず、索引でも今のファイルでも 1 回しか現れない行を対応づけ、今の行番号が増えていく最長の並びだけを固定する。残りの行(`Run();` のように何度も現れる行)は、前後の固定した行の間だけを二分探索で探す。関数を 1 つ消しても、後ろの関数の同じ文字列の行を取り違えない
  - 見つからない行(書き換えた行・消した行)は、最も近い対応のついた行のずれから推定し、その旨を付ける。コメントと無効な `#if` の範囲も同じだけ動かす
  - 構成ごとに索引の新しさが違うときは、同じ参照(行以外が同じ)に付け直しの要らない構成の行があれば、そちらを採り、古い構成の推定した行は捨てる
  - 限界: 同じ文字列の行が別の場所にもあると、書き換えた行がそこに「移った」と判定されることがある(注記は付く)。行の順序が変わる編集(関数の入れ替え)は推定になる
  - コードベース B のある .cpp の先頭に 3 行足し 1 行を書き換えると、10 件の呼び出しはすべて今の行を指した(書き換えた行は推定)。問い合わせは約 0.5 秒。2 万行・手がかり 5,000 行のファイルを全行書き換えても、付け直しは 0.03 秒【実測】
- **鮮度の表示**: 出力の先頭に、索引の後に変わったファイル、索引の後に変わったのにどの構成も読んでいないソース(新しいファイルの候補)、消えた TU を出す。判定はファイルの更新日時で、最も古い索引を基準にする
  - 「読んだファイル」は、ltidx が TU ごとに記録した、TU が読んだルート配下のファイル(`.deps.tsv`)。それが無い古い索引では、TU の主ファイル、コメントか無効な `#if` のあるファイル、索引に行のあるファイルで代える(参照もコメントも無いヘッダーは数えられない)
- **増分更新(`ltidx -update`)**: 前回の索引と比べ、新しい TU・前回失敗した TU・コンパイルのコマンド(ハッシュを `.tu.tsv` に記録)が変わった TU・前回の後に変わった(消えた)ファイルを読む TU だけを解析し直す
  - 前回の行を捨てるのは、変わったファイルの行と、解析し直す TU か消えた TU だけが読んでいたファイルの行。ほかの TU も読む変わっていないヘッダーの行は残して新しい行を足す(行ごとに、どの TU から出たかは記録していない)。そのため、変わっていない共有のヘッダーに、テンプレートの実体化などで生じた古い行が残りうる。行ごとの出どころを持つと、ヘッダーの行が TU の数だけ重複するので採らなかった
  - 索引の時刻は解析を始めた時刻にする。解析の途中で保存されたファイルも、次の更新で「変わった」と扱われる
  - 出力は一時ファイルに書いてから、4 つまとめて差し替える。Windows では開かれているファイルの名前を変えられない(Python の `open` は `FILE_SHARE_DELETE` を付けない)ので、まず古いほうを `.old` に退かせ、10 秒待っても退かせなければ何も変えずに失敗する。旧版の個別の差し替えでは、`.skip.tsv` を開いたままにすると `.tu.tsv` だけが新しくなった【実測: Fable のレビュー】
  - コマンドのハッシュには、索引の中身を変える ltidx のオプション(`-root`・`-source-cp`・`-no-dep` など)も含める。オプションを変えて `-update` すると全 TU を解析し直す
  - 変更を見るのはルート配下のファイルだけ。ルートの外の生成ヘッダーやサードパーティのヘッダーが変わっても、その TU は解析し直さない。include の探索に失敗したファイルも記録しないので、探索パスに同名のヘッダーが新しく置かれても気付かない
  - 文字コードの検査を足した前後で、コードベース B の全体の作り直しの時間は変わらなかった(8 並列で旧版 16.1〜16.3 秒、新版 16.3 秒)【実測】
  - コードベース B で、TU 4 つが読むヘッダーの先頭に 2 行足し、別の .cpp に関数を 1 つ足すと、6/194 TU(前回失敗した 1 TU を含む)を解析し直して 1.5 秒(全体の作り直しは 16.2 秒)。索引の行・コメントなどの範囲・読んだファイルの記録は、全体の作り直しと完全に一致した【実測】
  - 同時に、TU ごとにプロセスと作業ディレクトリを共有しないファイルシステム(`createPhysicalFileSystem`)を使うようにした。従来の既定の `getRealFileSystem` は作業ディレクトリをプロセスと共有し(「usually thread-hostile」)、`createPhysicalFileSystem` は独自の作業ディレクトリを持つ【公式: VirtualFileSystem.h】。ClangTool は TU ごとに作業ディレクトリをコンパイルのディレクトリに変えるので、従来は、TU ごとにディレクトリが違う `compile_commands.json` を並列に解析すると、作業ディレクトリを取り合いうる作りだった(発生は未確認)。変更の前後でコードベース B の索引は(`override` 行を除いて)完全に一致した【実測】
- **自動更新(MCP サーバー)**: `refs` / `check` のたびに、鮮度の判定(上の「鮮度の表示」と同じもの)で古いと分かれば、裏で作り直しを始めて最大 10 秒待つ。終わらなければ今の索引で答え、次の呼び出しから新しい索引を使う
  - 全部終わるまで待たないのは、作り直しの時間が編集で大きく変わるため。ふつうの .cpp 1 つで 0.5 秒、clang のヘッダーを読む ltidx.cpp 1 つで 3.9 秒(どちらも MCP の呼び出しの往復全体)【実測】、多くの TU が読むヘッダーでは全体の作り直し(Nox で 90〜120 秒)に近い
  - 待つ時間の既定は 10 秒。Copilot CLI の MCP の呼び出しの待ち時間の既定値は公式の文書に見つからず(サーバーごとに `--timeout <ms>` で変えられる【実測: copilot 1.0.105 の `mcp add --help`】)、Eclipse 版の 60 秒の固定の上限【既報: microsoft/copilot-for-eclipse#322】より十分短くした
  - 作り方は index-project が残す `<索引>.recipe.json` から取る。新しいソース・消えた TU があるときだけ `compile_commands.json` も make-cdb で作り直す(MSBuild を毎回は走らせない)。`.vcxproj` のコンパイルの設定だけの変更は、ソースの更新日時に出ないので拾えない
  - 同時に 1 つだけ。ロックは `update.lock` を開いたままにして示す。Windows では開かれたファイルを消せないので、消せればロックの持ち主はもういない(プロセスが落ちてもロックが残らない)
  - 解析し直す TU が無かった構成も、索引の時刻を作り直しの開始時刻まで進める。進めないと、どの TU も読まない新しいソースが毎回「古い」と判定され、呼び出しのたびに作り直す
  - 失敗したら、次にソースが変わるまで作り直さない(同じ失敗を呼び出しのたびに繰り返さない)
- **ltidx のソース行の不具合(修正済み)**: 列 1 のトークンの行で、前の行と連結したソース行を書いていた(`StringRef::rfind(C, From)` は `[0, From)` を探すので、`From` に `Off - 1` を渡すと直前の改行を見落とす【公式: StringRef.h】)。コードベース B で 120,777 行中 233 行。直した後は、Debug・Release の全 240,088 行で、索引のソース行と今のファイルの行が一致した【実測】。それより前に作った索引は作り直す

## 必ず確かめる落とし穴

- **Shift_JIS のソース**: 0x5C を 2 バイト目に持つ文字(表、ソ、能など)が `//` コメントの行末にあると行継続になり、次の行が消える。`clang -fsyntax-only` は exit 0 で、`-Wcomment` を付けて初めて警告が出る【実測】。rg はこの行を見つけるので、rg より悪い結果を「解析成功」と見せてしまう
  - ltidx の旧版で確かめると、`// 表` の次の行の呼び出しが索引から消え(コメントの範囲が次の行まで伸びる)、文字列 `"表"` を含む TU は `expected expression` で失敗した【実測】
  - 対応(済み): ltidx はファイルを読む層(VFS)で、UTF-8 として正しくないソースをコードページで UTF-8 に直してから clang に渡す。cl は BOM の無いソースを ANSI コードページで読むので、既定はそれに合わせ、TU の `/source-charset:` を優先する。clang-cl は UTF-8 以外の `/source-charset:`・`/execution-charset:` をエラーにする【実測】ので外す。UTF-16(BOM 付き)も直す。直したファイルは、大きさも直した後のものを返す(SourceManager が読んだ大きさと突き合わせる)
  - 索引の列番号とソース行は直した後の UTF-8 のもの。ltq もテキスト検索と行の付け直しの前に同じ変換をする。変換しないと、Shift_JIS の 2 バイト目(0x40〜0x7E)が英字になって偽の単語一致が出るうえ、列がずれてコメントの範囲の判定を誤る
  - UTF-8 として正しいソースは、cl と違ってコードページに関係なく UTF-8 として読む(cl は `/utf-8` が無ければ ANSI コードページで読み、C4819 を出す)
- **TU の成否**は戻り値ではなく診断の深刻度で判定する(致命的でないエラーでも 0 が返る)【実測】
- **作業ツリーの状態**: 未コミットの変更で消えたヘッダーを別のヘッダーがまだ include していると、それだけで多数の TU が失敗する(Nox で 129 件)【実測】。TU の失敗は必ず出力に出す
- **`compile_commands.json` の加工**: PCH の除去で `/Fp` を大文字小文字を区別せずに消すと `/fp:precise` も消える

## ltidx の構築

- **LLVM**: 公式リリースの `clang+llvm-23.1.4-x86_64-pc-windows-msvc.tar.xz`(約 900 MB、展開後 4.1 GB)を使う。MSI は `LLVM_INSTALL_TOOLCHAIN_ONLY=ON` で開発用ライブラリを含まない【公式: build_llvm_release.bat】
  - `include` と `lib` だけでは足りない。`LLVMExports.cmake` が `bin` の実行ファイルの存在を確かめる【実測】
  - CI(GitHub Actions の windows-latest)では、配布物から `include` と `lib`(約 700 MB)だけを取り出し、エクスポートに載る `bin` の 110 ファイルを空のファイルで置く。ビルドとテストが通り、ジョブ全体は約 1 分 45 秒【実測】
  - 配布物は `/MT`、RTTI なしなので、ツールも `/MT /GR-` でビルドする
  - zlib・zstd は同梱されていない。ltidx は圧縮を使わないので `zstub.c` で代替する
- **重複の除き方**: 実体化ごとに呼び出し元の名前が変わり、Nox で 153 万行(349 MB)になった。修飾名からテンプレート引数を外し、名前空間の行を出さないようにすると 16.9 万行(41 MB)になった【実測】
- **Nox 全体(Debug|x64)**: 362/367 TU が成功。8 並列・最低優先度で 90〜120 秒、メモリは最大約 4.3 GB【実測】

## compile_commands.json の自動生成

導入の手間を減らすため、`scripts/make-cdb.ps1` が Visual Studio のソリューションか CMake から作る。`index-project` は、`compile_commands.json` が無ければこれを呼ぶ。

- **Visual Studio(.slnx / .sln / .vcxproj)**: MSBuild の `GetClCommandLines` ターゲット(`Microsoft.Cpp.DesignTime.targets`、IntelliSense 用)が、ファイルごとの cl のコマンドライン・作業フォルダ・ファイルの一覧を返す。MSBuild 17.8 以降の `-getTargetResult` で、ビルドせずに JSON で取れる【実測: MSBuild 18.11】。全プロジェクトを 1 つの .proj から `MSBuild` タスクで並列に呼ぶ
  - 設定(`ClCompile` のメタデータ)から cl のオプションを組み立てる案は採らなかった。CL タスクの変換の規則を自前で持つことになり、漏れる
  - 「VC++ ディレクトリ」の `IncludePath`・`ExternalIncludePath` は、CL タスクが環境変数 `INCLUDE` で渡すのでコマンドラインに無い。プロジェクトに足したターゲットで値を取って足す。`IncludePath` に自分で足したフォルダは `/I`、`ExternalIncludePath` と VS・SDK の既定のフォルダは `/imsvc`。最初は全部 `/imsvc` にしていたが、システムのヘッダー扱いになり、そこにある自前のヘッダーの定義・参照が索引から丸ごと消えた【実測: Fable のレビュー】
  - 要求した構成・プラットフォームを持たないプロジェクト(Win32 だけのプロジェクトを x64 で読むなど)を、MSBuild はエラーにせず、その構成の設定(include・マクロ)が抜けたコマンドラインを返す【実測】。.vcxproj の `ProjectConfiguration` を見て、無ければ読まずに警告する
  - 全プロジェクトを 1 回の `MSBuild` タスクで呼ぶと、1 つの評価エラー(`Import` 先が無いなど)で全部の結果が消えた【実測】。`%(Identity)` でバッチにして、プロジェクトごとに呼ぶ
  - コードベース B を CMake の Visual Studio 18 2026 ジェネレーターで .slnx にし、そこから作った `compile_commands.json` は、Ninja のものと TU の集合(194 ファイル・222 件)が同じで、索引は全 122,603 行が一致した。取り出しは 1.8 秒【実測】
- **CMake**: VS 同梱の CMake と Ninja で構成だけ行う。`vcvarsall.bat` の後の PATH の書き換えは、`cmd /c` の 1 行の中では `%PATH%` が先に展開されて効かないので、cmake と ninja はフルパスで渡す【実測】
- どちらもビルドはしないので、ビルドで生成されるヘッダーを読む TU は失敗する(TU の失敗として ltq の出力に出る)

## 大規模なコードでの速さ

コードベース B の写しを 20 個並べた合成のコード(ソース約 2 万ファイル・約 560 MB、索引 480 MB・245 万行)で ltq を測った【実測】。

| 問い合わせ | 旧版 | 新版 | 参考: rg 1 回 |
|---|---|---|---|
| `refs`(E1〜E4 の 4 問) | 4.0〜8.3 秒 | 1.9〜4.6 秒 | 0.77 秒(E1 の名前で `rg -w -n`) |
| `check` | 3.6 秒 | 0.8 秒 | — |

- 旧版は、索引の全行を Python で 2 回(参照の抜き出しと「読んだファイル」の集計)、ソースの全バイトを 1 回(行の先頭の数え上げ)なめていた。新版は、索引を mmap して記号の列の末尾(`<名前><TAB>`)だけを C の速さで探し、読んだファイルは `.deps.tsv` から取り、行番号は一致の間だけ数える。出力は旧版と同じ(コードベース B と合成のコードの 10 問で 1 バイトも変わらない。Fable のレビューでも、合成の索引 32 通りで一致した)。ただし、テキスト一致の並びは旧版の os.walk の順(NTFS の列挙順)を小文字の名前順で真似ているので、`_` で始まる名前などがあると並びが変わりうる
- 残りの時間は、索引とソースを 1 回ずつ通して読む分で、規模に比例する。1 回の問い合わせは rg の 1 回より遅いが、rg だけの条件はモデルの往復と `view` が多い(コードベース B の E2 で 1 回 13〜24 回の `view`)ので、問い合わせ 1 回あたりの数秒は往復の削減で取り返せる見込み【推測】。これより大きいコードでは、索引に名前ごとの目次を持たせる必要がある(未実装)
- ripgrep は Copilot CLI が自分のフォルダに同梱していて PATH には無い【実測】ので、ltq からは呼ばない

## 採らなかった案

| 案 | 理由 |
|---|---|
| 問い合わせのたびに解析 | 1 TU で 0.5 秒以上かかり、rg に勝てない【実測】 |
| clangd の索引を流用 | テンプレートの実体化を含まない【公式】 |
| scip-clang | 配布バイナリは Linux と macOS のみ【公式】 |
| 既存の clangd 系 MCP | clangd の取りこぼしを継承する |
| LLVM の自前ビルド | マシン負荷が大きい。公式の tar で足りた |

## 未解決

- 増分更新は、変わっていない共有のヘッダーにある古い行(実体化由来など)を消さない。ltq は `compile_commands.json` を知らないので、新しい TU の候補は「索引より新しく、どの構成も読んでいないソース」で出すだけ(`-update` は `compile_commands.json` と突き合わせる)
- `virtual dispatch` の節は、計測(段階 3、コードベース B)の後に足した。上の表の数字はこの節の無い版のもの。コードベース B の E3 の誤答(派生クラスへの呼び出しを足した)を防ぐ見込みだが、測っていない【推測】
- **用途に応じた切り替え**は測っていない。これまでの問題はすべて C++ の記号の参照を探すもので、ripgrep が向く問題(文字列・ログの文言・設定ファイル・C++ 以外のファイル)で、エージェントが ltq を誤って使ったり往復が増えたりしないかは分からない
- 大規模なコードは合成のもの(コードベース B の写し 20 個)でしか測っていない。実際の大規模なコードベースでの索引の作成時間・問い合わせの速さ・正答率は未確認
- 別プラットフォーム向けの構成(Metal、Vulkan など)は、Windows では `compile_commands.json` を作れないことが多く、統合の仕組みがあっても索引に載らない
- 古いコンパイラ向けのコード(独自拡張・古い規格)での解析成功率。Shift_JIS は対応したが、実際の Shift_JIS のコードベースでは測っていない
- 索引に無いファイル(別プラットフォーム向けのコードなど)の一致は、ltq がディレクトリごとの件数を返すだけで、判定はモデルに任される。コードベース B では、ここで誤答が 1 回出た。別の構成で作った索引を足せば索引に載る(構成ごとの索引の統合と同じ課題)
