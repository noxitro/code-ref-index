# ltidx — C++ の参照索引を作る

## 目的

`compile_commands.json` に載っている TU を clang の libtooling(`clang::index`)で解析し、プロジェクト内の参照を 1 行 1 件の TSV に出します。
問い合わせのたびに解析し直す必要がありません。テンプレートの実体化の中の呼び出しも拾います。問い合わせには `../query` の `ltq` を使います(TSV を `rg` で直接引くこともできます)。

設計の背景は `../docs/design.md` を参照してください。

## 前提

- Windows と Visual Studio 2026(18)の C++ ツール。CMake と Ninja は VS 同梱のものを使います
- LLVM の公式配布物 `clang+llvm-<版>-x86_64-pc-windows-msvc.tar.xz` を展開したフォルダ(`include`・`lib`・`bin` が要ります)。動作を確かめた版は 23.1.4 です
  - MSI 版は開発用のライブラリを含まないので使えません

## ビルド

`build.bat` をダブルクリックします。`build\ltidx.exe` ができます(Release、並列 4)。
LLVM の場所は、環境変数 `LLVM_ROOT` か、このフォルダの `llvm-root.txt`(1 行目に展開先のフォルダを書く。git には入りません)で指定します。

```bat
set LLVM_ROOT=D:\llvm\clang+llvm-23.1.4-x86_64-pc-windows-msvc
build.bat
```

## テスト

`test\run_test.bat` をダブルクリックします。すべて通れば `PASS` と出ます(Python 3.10 以降が要ります)。

- `test\sample.cpp` を索引にして、`test\expected*.tsv` と比べます。コメント内・無効な `#if` の中・テンプレート内の using 宣言越しの呼び出し・未解決の呼び出しを含みます
- `test\werror.cpp` で、`/WX` 付きの TU が失敗しないことを確かめます
- `test\test_ltidx.py` で、一時フォルダに作った小さなプロジェクトを索引にします。Shift_JIS・UTF-16 のソース、`/source-charset`、仮想関数の上書き、`-update` の結果が全体の作り直しと一致することを確かめます

## 使い方

```bat
ltidx.exe -p <compile_commands.json のあるフォルダ> -root <索引に含めるソースのルート> -o <出力.tsv> [-j 並列数] [-update] [-source-cp コードページ] [-delayed] [-no-inst] [-no-dep] [対象ファイル...]
```

- 優先度を下げて実行するには `start "" /low /wait /b ltidx.exe ...` を使います
- 出力は 4 つです。書き終えてから 4 つまとめて差し替えるので、作っている途中の索引や新旧の混ざった索引を ltq が読むことはありません(ltq などが開いていれば 10 秒まで待ち、それでも開いていれば前の索引を残して終了コード 2 で終わります)。ファイルの更新日時は、解析を始めた時刻にします(解析の途中で変わったファイルも、次の `-update` と ltq が「索引の後に変わった」と扱います)
  - `<出力.tsv>` … `記号 <TAB> 役割 <TAB> 呼び出し元 <TAB> path:line:col <TAB> ソース行`
    - 役割は `def` `decl` `call` `write` `ref` `dep` `override` のどれかです。暗黙の参照は `-implicit` が付きます
    - 呼び出し元は、その参照を含む関数です
    - `override` は仮想関数の上書きです。記号は上書きするメソッド、3 列目は上書きされる基底のメソッドです(呼び出し元ではありません)。基底のポインタや参照越しの呼び出しは基底のメソッドに解決されるので、ltq がこの行から上書きの関係を辿ります
    - 記号は修飾名で、テンプレート引数は付けません(`Foo<int>::f` は `Foo::f`)
    - `dep` は、テンプレートの中で解決先が決まらない呼び出し・参照です(`t.f()`、`this->f()`、`Base::f()` など)。記号は `?::f` の形で、名前しか分かりません。`-no-dep` を付けると出しません
    - テンプレート内の `using Base::f;` を経由した参照は、clang の索引では using 宣言(`派生::f`)にしか向きません。ltidx は TU の終わりにそのクラステンプレートの実体化を調べ、宣言の先(`基底::f`)の行も `-using` を付けて出します
  - `<出力.tsv>.tu.tsv` … TU ごとの成否・エラー数・秒数・新規行数・最初のエラー・コンパイルのコマンドのハッシュ・ソースを読んだコードページ。**失敗した TU の参照は索引に無い**ので、検索結果の網羅度はここで確かめます
  - `<出力.tsv>.skip.tsv` … `path <TAB> 種類 <TAB> 開始 line:col <TAB> 終了 line:col`。種類は `comment`(コメント)か `inactive`(無効な `#if` の分岐)です。`ltq` が、テキスト検索の一致が索引に無い理由を答えるのに使います
  - `<出力.tsv>.deps.tsv` … `TU <TAB> path`。TU が読んだルート配下のファイルです。`-update` と、ltq の鮮度の判定に使います
- `-update` … 前回の索引(同じ `-o`)と比べて、次の TU だけを解析し直して差し替えます。前回の索引は `.deps.tsv` 付き(この版以降)である必要があります
  - 新しい TU、前回失敗した TU、コンパイルのコマンドが変わった TU、前回の後に変わった(消えた)ファイルを読む TU
  - `compile_commands.json` から消えた TU は索引から外します
  - ltidx のオプション(`-root`・`-source-cp`・`-no-dep` など)を変えたときは、全 TU を解析し直します
  - 変更を見るのはルート配下のファイルだけです。ルートの外にある生成ヘッダーやサードパーティのヘッダーを変えたときは、全体を作り直してください
  - 前回の行を捨てるのは、変わったファイルと、解析し直す TU か消えた TU だけが読んでいたファイルの行です。ほかの TU も読む、変わっていないヘッダーの行は残して新しい行を足すので、そこにテンプレートの実体化などで生じた古い行が残ることがあります。気になるときは全体を作り直してください
- 文字コード: UTF-8 として正しくないソースは、cl と同じくコードページで読み、UTF-8 に直して解析します。UTF-16(BOM 付き)も UTF-8 に直します
  - コードページは、TU の `/source-charset:` か `-finput-charset=` があればそれ、無ければ `-source-cp`、それも無ければこの PC の ANSI コードページです(日本語版 Windows なら 932 = Shift_JIS)。`/utf-8` の TU では変換しません(UTF-16 を除く)
  - clang-cl は UTF-8 以外の `/source-charset:` と `/execution-charset:` をエラーにするので、外して解析します
  - 直さないと、Shift_JIS の「表」「ソ」「能」などの 2 バイト目(`\`)が行の継続や文字列のエスケープになり、`//` コメントが次の行を飲んだり TU が失敗したりします
  - 索引の列番号とソース行は、UTF-8 に直した後のものです。ltq も同じ変換をして突き合わせます
- `-delayed` を付けないときは `/Zc:twoPhase` を足し、遅延テンプレート解析を止めます。これで、一度も実体化されないテンプレート本体の非依存呼び出しも索引に載ります
- `-no-inst` は比較用です。テンプレートの暗黙の実体化を索引しません
- PCH の指定(`/Yu` `/Yc` `/Fp`)は外して解析します
- 警告をエラーにする指定(`/WX` `-Werror` `-Werror=…`)は外して解析します。cl に無い clang の警告(`override` の付け忘れなど)で TU が失敗扱いになるのを防ぎます

TSV を直接引く例:

```bat
rg "^Circle::update\tcall" index.tsv
rg "\tcall\tmain\t" index.tsv
```

## 制約

- 配布物の LLVM は zlib / zstd を同梱しないため、`zstub.c` で代替しています。`crc32` は zlib と同じ結果を返します。圧縮・展開は常に失敗を返しますが、ltidx は使いません
- 同じ行が複数の TU から出たときは 1 行にまとめます。構成(Debug/Release など)ごとの索引は別々に作り、ltq がまとめて引きます
- `-using` の解決は、その TU にあるクラステンプレートの実体化から引きます。実体化が無いときや、using 宣言が部分特殊化の中にあるときは、using 宣言の行だけが残ります
